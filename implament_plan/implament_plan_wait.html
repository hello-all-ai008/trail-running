สแกนซ้ำ (duplicate) — ไม่ insert เข้า scan_events แล้ว คงข้อความหน้าเว็บเหมือนเดิม

Gong ทดสอบสแกน BIB จริงครั้งแรกวันนี้ — สแกนซ้ำ BIB เดิม หน้าเว็บขึ้นข้อความ "duplicate" ถูกต้อง แต่ใน Supabase ยังเห็นแถวใหม่ insert เข้า scan_events (status = DUPLICATE) ทุกครั้งที่สแกนซ้ำ — Gong อยากให้หน้าเว็บ ขึ้นข้อความเหมือนเดิม แต่ไม่ต้อง insert เข้า database

ตรวจโค้ดแล้ว — เจอว่าไม่ใช่บั๊ก เป็น design เดิมที่ตั้งใจ

ระบบตรวจจับซ้ำถูกต้อง 100% อยู่แล้ว — decideOutcome() เช็คว่ามี scan VALID ที่ checkpoint เดียวกันมาก่อนไหม เจอก็ตอบ "duplicate" กลับไป ไม่เคยไปเปลี่ยนสถานะ runner ซ้ำ (transitionRunner ทำงานเฉพาะตอนผล VALID เท่านั้น) — ไม่มีความเสี่ยงข้อมูลพังไม่ว่าจะแก้หรือไม่แก้เรื่องนี้

ที่มันยัง insert เข้า DB เพราะ scan_events ถูกออกแบบเป็น append-only audit log — log "ทุกครั้งที่สแกน ไม่ว่าผลจะเป็นอะไร" (ตามที่เขียนไว้ใน division-backend/CLAUDE.md) ไว้เพื่อย้อนดูทีหลังได้ ว่าเครื่องสแกนพัง หรือมีใครสแกนซ้ำหลายรอบผิดปกติไหม

Trade-off ที่คุยกับ Gong แล้ว: ถ้าตัด insert ทิ้งตอน duplicate จะเสีย audit trail ตรงนี้ถาวร — ย้อนดูไม่ได้อีกว่ามีการสแกนซ้ำกี่ครั้ง เมื่อไหร่ (เผื่อวันแข่งจริงต้องสืบปัญหาเครื่องสแกน/คนกดซ้ำ) Gong ยืนยันแล้วว่าตัดออกไปเลย — ไม่ insert duplicate อีกต่อไป

จุดที่แก้ — เฉพาะ DUPLICATE เท่านั้น

division-backend/internal/scan/apply.go ฟังก์ชัน Apply() — ครอบเงื่อนไขรอบการเรียก logScan() ให้ข้ามเฉพาะตอนผลเป็น OutcomeDuplicate เท่านั้น

outcome, err := decideOutcome(ctx, pgxScanHistory{tx: tx}, runnerID, req.CheckpointCode) if err != nil { return Result{}, fmt.Errorf("decide outcome: %w", err) } + if outcome != OutcomeDuplicate { if err := logScan(ctx, tx, req.RawValue, &runnerID, req.CheckpointCode, req.StationID, recordedBy, outcome, ""); err != nil { return Result{}, err } + }

ส่วนที่เหลือ (อ่านข้อมูล runner ส่งกลับ, response ที่ frontend ได้รับ) ไม่แตะเลย — หน้าเว็บยังได้ outcome: "duplicate" เหมือนเดิมทุกอย่าง แค่ไม่มีแถวใหม่เขียนลง DB

ขอบเขตแคบมาก: เฉพาะผล DUPLICATE เท่านั้นที่ไม่ insert — ผล NOT_FOUND, NOT_CHECKED_IN, OK (VALID) ยัง log เหมือนเดิมทุกอย่าง ไม่แตะ

เจอเพิ่มระหว่างตรวจโค้ด (ไม่อยู่ในสโคปนี้ แจ้งไว้เฉยๆ)

  • Race condition เล็กๆ: ถ้าสแกนพร้อมกัน 2 คำขอในเสี้ยววินาทีเดียวกัน (2 สถานีพร้อมกัน) มีโอกาสน้อยมากที่ทั้งคู่จะผ่านเป็น VALID พร้อมกัน (ไม่มี lock กันไว้) — ไม่เกี่ยวกับเรื่องนี้ แยกไปทำทีหลังถ้าจำเป็น
  • LedBoard.jsx ตอนสแกนถูกต้อง (ไม่ใช่ duplicate) ในโหมดจริง เวลาที่โชว์บนจอ LED อาจว่างเป็นขีด — เพราะ field result.time ไม่มีในโหมดจริง — บั๊กเล็กๆ แยกไปทำทีหลัง

การตรวจ

  1. cd division-backend && go build ./... && go vet ./... — compile ผ่านสะอาด
  2. go test ./... — เทสเดิมทั้งหมดทดสอบ decideOutcome() ตรงๆ (ไม่แตะ DB) ไม่กระทบจากการแก้นี้
  3. รีสตาร์ท Go API ตัวที่รันอยู่ (local, port 8080) ให้ได้ binary ใหม่
  4. ทดสอบจริงผ่านหน้าเว็บที่ต่อ live mode อยู่แล้ว: สแกน BIB ที่ Check-in ครั้งแรก (นับแถวใน scan_events +1, status VALID) → สแกน BIB เดิมซ้ำ (หน้าเว็บขึ้น "duplicate" เหมือนเดิม) → เช็ค Supabase ว่าจำนวนแถวไม่เพิ่มจากการสแกนครั้งที่สอง

ดูแล้วโอเคบอก "ลุยได้" — ยังไม่ได้แก้โค้ด รอ Gong ตรวจก่อน
