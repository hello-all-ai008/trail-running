02 Frontend — division-frontend/

เขียนด้วย React 19.2.7 + Vite 8.1.1 + Tailwind CSS 4.3.2 (ผ่าน @tailwindcss/vite, ไม่มี PostCSS config แยก). ไม่มี state library (Redux/Zustand) — ใช้ hooks ล้วนๆ ผ่าน useRaceState. Routing เป็น custom hash router (useHashRoute) ไม่ใช้ react-router.

Data mode — dual switch

Toggle ผ่าน VITE_USE_MOCK_DATA (default = mock/true):

  • Mock mode: state อยู่ใน React + persist ลง localStorage (tt:v2:runners, tt:v2:scanLog)
  • Real mode: Supabase Auth (staff login) + Realtime subscribe (live_progress table) + fetch ไปที่ Go API (/runners, /scan) พร้อม JWT bearer

Testing Partial — logic only

8 test files, ทั้งหมดเป็น logic-level (Vitest, ไม่มี testing-library): bibNumbering.test.js, bibTemplate.test.js, monitor.test.js, raceEngine.test.js, registration.test.js, results.test.js, useBibConfig.test.js, monitor.feed.test.js. ไม่มี test สักตัวสำหรับ page/component จริง, ไม่มี test ของ api.js หรือ useRaceState.js.

Known gap ยืนยันจากโค้ดจริง (useRaceState.js comment): scan log ใน real mode เป็นแบบ per-device เท่านั้น — เครื่อง checkpoint แต่ละจุดเห็นแค่ scan ของตัวเอง ยังไม่ sync ข้ามสถานี เพราะ backend ยังไม่มี scan-log read endpoint.

03 Backend — division-backend/ + supabase/

Go 1.26.2, routing ด้วย stdlib net/http.ServeMux (ไม่ใช้ router library), DB ผ่าน pgx/v5 + pgxpool ตรงไปที่ Postgres (Supabase). Auth ผ่าน JWT + JWKS (golang-jwt/v5, MicahParks/keyfunc).

Endpoints ที่มีจริง Live

GET  /healthz                    (no auth)
POST /scan                       (staff auth)
GET  /runners                    (staff auth)
GET  /runners/{bib}/report       (staff auth)
GET  /checkpoints                (staff auth)
GET  /stats                      (staff auth)
GET  /results                    (staff auth)
GET  /results/export.csv         (staff auth)

Schema (supabase/migrations/0001-0005)

  • race_categories, checkpoints, runners, rfid_tags (ยังไม่ใช้จริง)
  • scan_events — append-only log, source of truth ของทุก scan
  • live_progress — PII-light, key ด้วย bib, ใช้ยิง Realtime
  • staff_users, registrations (self-serve staging แยกต่างหาก ยังไม่ link กับ runners)

Auth model

Go verify JWT ผ่าน JWKS ของ Supabase → lookup staff_users เอา role. Go เชื่อมต่อ DB ด้วย postgres role → RLS ไม่มีผลกับ Go เลย — RLS เป็นแค่ defense-in-depth, authorization จริงอยู่ที่โค้ด Go (internal/scan).

Testing Minimal

1 test file: internal/scan/apply_test.go (10 table-driven test, pure function, ไม่แตะ DB จริง). ไม่มี HTTP-level, integration, หรือ DB-backed test เลย — handlers, auth, raceview, results ไม่มี test คุ้มครองเลย

ยังไม่ทำ (ยืนยันจากโค้ด ตรงกับที่ CLAUDE.md บอก)

  • BIB/RFID admin endpoints (Step 2-3) — ไม่มี package bib/ หรือ rfid/
  • Excel import (Step 1) ใน Go — ไม่มี route
  • Scan-log read-back endpoint — มีแค่ POST /scan, ไม่มี endpoint อ่านคืน

Scalability flags ที่เจอในโค้ด

  • pgxpool ไม่ได้ set MaxConns/MinConns — ใช้ default ล้วนๆ
  • ไม่มี rate limiting เลย (golang.org/x/time อยู่ใน go.mod แต่ไม่มีไฟล์ไหน import ใช้จริง)
  • ไม่มี pagination บน list query ไหนเลย (ListAll, runner.List, results.List) — โค้ด comment ระบุ assumption ไว้ที่ ~2000 runner ต่อ race
  • CORS เปิดกว้าง Access-Control-Allow-Origin: * — comment ในโค้ดเองบอก "tighten once frontend domain fixed"

05 Capacity / จำนวน user สูงสุด

ไม่มี hardcode limit ในโค้ดที่ไหนเลย — ตัวเลขข้างล่างเป็นการประเมินจาก infra config จริง ไม่ใช่ load-test

Staff scan stations (concurrent)

Fly.io VM เดี่ยว + Supabase session pooler (ไม่ได้ tune pool size) → รองรับ staff scan station หลักสิบ connection พร้อมกันแบบสบายๆ

ถ้าใช้ Render free

Idle spin-down = ใช้งานแบบ always-on ไม่ได้เลย ไม่ว่าจำนวน user จะเท่าไหร่ — บล็อกทั้งวันแข่งจริง

Public/spectator viewer (live_progress)

จำกัดโดย Supabase Realtime connection limit ของ plan (free ~200 concurrent connection โดยทั่วไป) — เป็น limit ฝั่ง Supabase ไม่ใช่โค้ดใน repo นี้

จำนวน runner ต่อ race

ไม่มี pagination → assumption ในโค้ดอยู่ที่ ~2000 runner ก่อน list endpoint เริ่มหนัก

สรุปรวม: ระบบตอนนี้ fit กับ race ขนาดเล็ก-กลาง งานเดียว — staff scan station ไม่กี่จุด, runner หลักร้อย, ไม่มี public dashboard ที่ concurrency สูง ยังไม่ถูกออกแบบมาสำหรับ scale ใหญ่หรือแข่งพร้อมกันหลายงาน

06 จุดที่ควรแก้ (เรียงตามความสำคัญ)

  1. แก้ conflict Render vs Fly.io — เลือกตัวเดียว ลบอีกตัว อัปเดต CLAUDE.md ให้ตรงความจริง
  2. ไม่มี integration test ฝั่ง backend, ไม่มี component test ฝั่ง frontend เลย — เสี่ยงสุดเพราะ "wrong runner data = real dispute วันแข่งจริง" ตามที่ CLAUDE.md ระบุเอง
  3. ไม่มี pagination บน list endpoint — ต้องเพิ่มก่อน scale เกิน ~2000 runner
  4. CORS เปิดกว้างทุก origin — ต้อง lock ก่อนขึ้นจริง
  5. ไม่มี rate limiting บน /scan หรือ endpoint ไหนเลย — scanner client ค้าง/ลูปอาจถล่ม API
  6. ไม่มี endpoint อ่านคืน scan_events — scan log ฝั่ง frontend เป็น per-device คุยกันข้ามสถานีไม่ได้
  7. ไม่มี CI/CD — ไม่มี automated check ก่อน deploy เลย
