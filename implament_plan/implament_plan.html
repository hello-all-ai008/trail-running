หน้า BIB โหลดช้า — เพราะดึง @react-pdf/renderer มาแค่พรีวิว

รอบก่อนลดพรีวิวจากทั้งชุด (43 หน้า) เหลือ 1 ใบไปแล้ว แต่หน้ายังรู้สึกช้าตอนเปิด — Gong ถามหาสาเหตุจริง สาเหตุคือไลบรารี PDF เอง (@react-pdf/renderer, fontkit + PDF engine ~480KB gzip) ถูกโหลดมาทำงาน ทุกครั้งที่เปิดหน้า ทั้งที่ 90% ของการเข้าหน้านี้คือ "ดูดีไซน์" ไม่ใช่ "กดดาวน์โหลด"

ยังไม่ได้ลงมือ — รอ Gong ดูไฟล์นี้ก่อน ตามกติกา "เขียนแผนก่อนแตะโค้ดทุกครั้ง"

ตอนนี้เกิดอะไรขึ้น

เปิดหน้า BIB → โหลด @react-pdf/renderer ทั้งก้อน (480KB gzip) → PDFViewer สร้างไฟล์ PDF จริง + เมาท์ iframe แสดงผล → เห็นตัวอย่าง 1 ใบ

ปัญหาไม่ใช่จำนวนหน้าอีกแล้ว (แก้รอบก่อนแล้ว) แต่คือตัวเอนจิน PDF เองมีต้นทุนคงที่สูง — แค่โชว์ 1 ใบ ก็ต้องพา fontkit + PDF layout engine ทั้งชุดมาทำงานเหมือนเดิม แถมพิมพ์เลข/ปรับ Prefix ทีนึงก็รันเอนจินใหม่ทุกครั้ง

ทางแก้ที่เสนอ

เปิดหน้า BIB → พรีวิวด้วย HTML/CSS ธรรมดา (ไม่มี react-pdf) → เห็นตัวอย่าง 1 ใบ ทันที
กด "ดาวน์โหลด PDF" → ตอนนี้ค่อยโหลด @react-pdf/renderer (ครั้งเดียว ตอนนี้เท่านั้น) → สร้าง PDF จริงครบทุกใบ + ดาวน์โหลด

พรีวิวเปลี่ยนไปวาดด้วย div/img/span ธรรมดา (ไม่โหลดไลบรารีอะไรเพิ่ม) — พิมพ์แก้ Prefix/จำนวนหลัก/จำนวน Check Point แล้วเห็นผลทันที ไม่มีดีเลย์ ส่วนไฟล์ PDF จริง (ที่ต้องแม่นทุกพิกเซลสำหรับพิมพ์) ยังใช้ @react-pdf/renderer เหมือนเดิม แค่ย้ายไปโหลดตอนกดดาวน์โหลดแทน ผ่าน import() แบบ dynamic ซึ่ง Vite จะแยกเป็นคนละไฟล์ (chunk) ให้อัตโนมัติ

รายละเอียด

1. พรีวิวใหม่แบบ HTML ล้วน

ไฟล์ใหม่ src/components/bib/BibTagPreview.jsx — วาด 1 ใบด้วย DOM ปกติ: แถบ Header (รูปที่อัปโหลด หรือ placeholder สีเทา), เลข BIB ใหญ่ (ใช้ generateBibNumbers() เดิมจาก lib/bibNumbering.js, เป็นแค่ฟังก์ชันคำนวณเลข ไม่เกี่ยวกับ react-pdf อยู่แล้ว), แถวกล่อง Start/Check Point/Finish, แถบ Footer

กติกาป้าย Check Point (1 กล่อง = "Check Point", มากกว่า 1 = "CP1..CPn") ตอนนี้เขียนซ้ำอยู่ใน BibDocument.jsx — ดึงออกมาเป็นฟังก์ชันกลางใน lib/bibNumbering.js ให้พรีวิวกับ PDF จริง ใช้กฎเดียวกัน ไม่ต้องแก้ 2 ที่ถ้าเปลี่ยนกติกาในอนาคต

2. ย้าย react-pdf ไปโหลดตอนดาวน์โหลด

src/pages/BibGeneratorPage.jsx — เอา import แบบ static ของ PDFViewer, PDFDownloadLink, BibDocument ออกจากหัวไฟล์ทั้งหมด แทนที่ด้วย:

async function onDownload() {
  setGenerating(true)
  const [{ pdf }, { default: BibDocument }] = await Promise.all([
    import('@react-pdf/renderer'),
    import('../components/bib/BibDocument'),
  ])
  const blob = await pdf(<BibDocument ... bibNumbers={bibNumbers} />).toBlob()
  // blob → object URL → <a download> ชั่วคราว → click → revoke
  // (แพทเทิร์นเดียวกับ downloadCSV() ใน src/lib/raceData.js:191-198 แค่เปลี่ยนเป็น PDF blob)
  setGenerating(false)
}

ปุ่มโชว์ "กำลังสร้าง PDF…" ระหว่างรอ เหมือนพฤติกรรมเดิมของ PDFDownloadLink ทุกอย่าง แค่เขียนเอง

ความเสี่ยง

1. พรีวิว HTML จะไม่ตรงพิกเซลกับ PDF จริง 100% — แยกตามสาเหตุ:
  • ระยะห่าง/ขนาดกล่อง — เกือบ 0% เพราะทั้งคู่ใช้ตัวเลข pt/px ตายตัวชุดเดียวกัน (แถบสูง 70pt, กล่อง 76×52pt ฯลฯ) copy มาใช้ตรงๆ
  • ฟอนต์ — ของจริงที่ต่างแน่ๆ: react-pdf ใช้ Helvetica เป็นค่าเริ่มต้น ส่วนพรีวิวถ้าไม่ตั้งเองจะสืบทอด system-ui ของแอป ต่างกันได้ ~5-15% ในความกว้างตัวอักษร — แก้ด้วยการตั้ง font-family: Helvetica, Arial, sans-serif ให้พรีวิวโดยตรง จะเหลือต่างแค่ ~1-3% (แค่ anti-aliasing ของเบราว์เซอร์ vs PDF renderer เอง แก้ต่อไม่ได้แต่ตาเปล่าแทบไม่เห็น)
ยอมรับได้เพราะพรีวิวมีไว้ดูดีไซน์คร่าวๆ ไฟล์ PDF ตอนดาวน์โหลดคือของจริงที่เอาไปพิมพ์
2. กดดาวน์โหลดครั้งแรกของเซสชันจะมีดีเลย์สั้นๆ (โหลด react-pdf ตอนนั้นแทน) — มีข้อความ "กำลังสร้าง PDF…" กันงงว่าไม่ได้ค้าง หลังจากนั้นเบราว์เซอร์แคชไว้ กดซ้ำจะไว

การตรวจ

cd division-frontend
npm test && npm run lint && npm run build
  1. ดู build output: มี chunk react-pdf แยกออกมาต่างหาก ไม่ได้ติดไปกับ chunk ของหน้า BibGeneratorPage
  2. เปิด DevTools → Network, เข้าหน้า "สร้าง BIB (PDF)" — หน้าขึ้นเร็ว ไม่มี request โหลดก้อน react-pdf (~480KB) จนกว่าจะกดดาวน์โหลด
  3. พิมพ์แก้ Prefix / จำนวนหลักรวม / จำนวน Check Point — พรีวิวอัปเดตทันที ไม่มีดีเลย์
  4. กด "ดาวน์โหลด PDF" — เห็น "กำลังสร้าง PDF…" ระหว่างรอ, ไฟล์ที่ได้ถูกต้องเหมือนที่ตรวจผ่านรอบก่อน (เช่น MKT33 Prefix "3" → 3001, 3002… CP1/CP2/CP3 ถูกต้อง, จัดหน้าคว่ำ 2 ใบต่อแผ่นเหมือนเดิม)

ดูแล้วโอเคบอก "ลุยได้" — ไม่มีจุดไหนต้องให้ Gong ตัดสินใจเพิ่ม เป็นแค่การย้ายว่าไลบรารีหนักโหลดตอนไหน ไม่เปลี่ยนพฤติกรรมที่ใช้งานจริง
